# Qwen3.6-27B 在 GR308 上的 vLLM 吞吐调优总结

> 更新时间：2026-09-11  
> 目标：在暂不要求输出准确性与一致性的前提下，提高 Qwen3.6-27B 在 GR308/FANT GPU 上的推理吞吐。  
> 本文只记录已经执行的实验、结果和决策，不包含尚未验证的优化设想。

## 1. 测试对象与统一口径

### 1.1 硬件和部署拓扑

- 服务器包含 4 张物理卡，每张卡为双芯结构，共暴露 8 个逻辑 GPU。
- 当前部署拓扑为 `4 × TP2`：逻辑卡对分别为 `0,1`、`2,3`、`4,5`、`6,7`。
- 每个 TP2 副本并发为 C16，整机总并发为 C64。
- 推理后端为厂商 vLLM 0.18/FANT 适配镜像。

### 1.2 模型和请求参数

| 项目 | 配置 |
|---|---|
| 模型 | Qwen3.6-27B |
| 权重基线精度 | BF16 |
| 优化候选精度 | FP16 |
| 输入长度 | 3072 tokens |
| 输出长度 | 1024 tokens |
| 单副本并发 | 16 |
| 整机并发 | 64 |
| 执行模式 | FANT Graph |
| TP | 每副本 TP2 |

### 1.3 指标定义

- **直接输出吞吐**：`全部实际生成 token 数 ÷ 端到端 wall-clock 时间`，单位为 tok/s。这是本文的主指标。
- **短 Decode 吞吐**：短输入、短输出扫描所得，只用于快速筛选，不能代替 3072→1024 正式结果。
- **Decode Avg TPS**：单请求或请求平均的 Decode 速率。该指标不能在未统一统计方法时直接与整机 wall-clock 吞吐比较。
- **TTFT**：Time To First Token，首 token 延迟。
- **抢占数**：因 KV Cache 容量不足导致的 preemption 次数。

## 2. BF16 Graph baseline

### 2.1 四个 TP2 副本

| TP2 副本 | 运行时长 | 直接输出吞吐 |
|---|---:|---:|
| GPU 0,1 | 897.424 s | 18.2567 tok/s |
| GPU 2,3 | 896.933 s | 18.2667 tok/s |
| GPU 4,5 | 900.452 s | 18.1953 tok/s |
| GPU 6,7 | 897.848 s | 18.2481 tok/s |
| **整机合计** | — | **72.781 tok/s** |

四个副本的单副本吞吐范围为 18.1953～18.2667 tok/s，硬件副本间差异较小。这里的四个副本属于同一次整机运行中的四个硬件实例，并不是四次独立随机重复实验。

### 2.2 KV blocks 关键基线修正

KV blocks 从 144 增加至 152 后：

- 整机吞吐从 46.455 tok/s 提升至 72.781 tok/s，提升 56.67%。
- KV 抢占次数从 144 次下降为 0 次。
- 该改动解决的是容量不足和抢占问题，是当前 BF16 baseline 中收益最大的已采用配置修正。

## 3. 已执行优化总表

| 优化方向 | 测试结果 | 性能判断 | 决策 |
|---|---|---|---|
| KV blocks：144→152 | 整机 46.455→72.781 tok/s，+56.67%；抢占 144→0 | 消除 KV 容量瓶颈，收益显著 | **采用** |
| KV blocks：160 | Prefill 阶段触发 HIP OOM | 超出安全显存范围 | 淘汰 |
| `max_num_batched_tokens=3072` | 短 Prefill 约快 1.44%，但 TTFT 变差、显存余量下降 | 局部收益不足以覆盖稳定性代价 | 暂不采用 |
| batched tokens：4096/8192 | HIP OOM | 显存不可承受 | 淘汰 |
| concurrent partial prefill | 厂商后端抛出 `NotImplementedError` | 当前软件栈不支持 | 不支持 |
| `max-num-seqs=16` 单项消融 | 310.879→376.430 s，慢 21.09% | 作为单项优化无收益 | 淘汰；最终配置中仅作为容量上限保留 |
| async scheduling | 短 Decode 33.499→33.469 tok/s，-0.09% | 无实际收益 | 淘汰 |
| 仅捕获 C16 Graph | 短 Decode 33.499→33.314 tok/s，-0.55% | 单独只捕获 C16 无收益 | 淘汰 |
| 捕获 C1/C2/C4/C8/C16 Graph | 覆盖实际 Decode batch 变化，运行稳定 | 作为最终 Graph 配置使用 | **采用** |
| O3/throughput 编译优化 | 厂商将 vLLM compilation backend 替换为 mock，无法导入 `VllmBackend` | 当前镜像不可用 | 不可用 |
| MTP1 初步扫描 | 短 Decode 曾达到约 37.5 tok/s；特定 KV120 配置达到 44.9 tok/s，对照约 28.3 tok/s | 短测试显示明显潜力 | 进入正式验证后否决 |
| MTP1 正式 3072→1024 | 16.159 tok/s，对比 BF16 baseline 约 -11.5%；同时出现抢占、请求失败或 OOM 风险 | 短 Decode 收益不能延续到长输出 | 淘汰 |
| MTP2 | 整体约 28.48 tok/s 的短测试表现，但 KV120 下只能稳定容纳约 11 个请求 | 无法满足单副本 C16 | 淘汰 |
| MTP allocator 128 MiB | 解决 sampler 约 122 MiB 连续内存 OOM，但随后出现 Graph OOM/RCCL 错误 | 只解决了中间故障，未形成稳定链路 | 冻结 |
| FHCCL channel/buffer/protocol 扫描 | 微基准有少量改善，完整 Prefill 测试反而慢约 8.25% | 端到端结果为负收益 | 淘汰 |
| vLLM custom all-reduce | 出现 DMA semaphore timeout，双芯死锁 | 稳定性不可接受 | 淘汰 |
| 直接调用厂商 fhBLAS | 与现有执行路径基本为同一类内核，未得到明显收益 | 没有可测端到端增益 | 淘汰 |
| 全局权重转置 | 单个 GEMM 明显加速，但整模型 Prefill 极慢，并出现通信/层间问题 | 局部 GEMM 优化破坏整体执行 | 淘汰 |
| Decode 双布局、逐层分配 | 触发 FANT VA 碎片以及 Graph/KV OOM | 显存和虚拟地址开销不可接受 | 淘汰 |
| Down Projection 原地转置 | Decode 微基准约 +17%，但 Prefill 严重退化 | 阶段间收益冲突 | 淘汰 |
| Slab24 | 启动或捕图阶段 OOM | 额外权重布局过大 | 淘汰 |
| Slab16 | 短 Decode 有收益；正式长输出出现 KV 抢占和容量抖动，10 分钟只完成约 2.1k/16.4k token | 长输出严重退化 | 中止并淘汰 |
| FP16+Slab8，短 Decode | 31.2357→37.1246 tok/s，约 +18.9% | 快速筛选表现突出 | 进入正式验证 |
| FP16+Slab8，短 Prefill | 327.060→322.433 s，约快 1.4% | 只有轻微局部改善 | 不足以单独决定采用 |
| FP16+Slab8，正式 3072→1024 | 912.562 s，17.9539 tok/s；相对 BF16 baseline 约 -1.7%，相对纯 FP16 约 -5.9% | 长上下文尾部延迟抵消短 Decode 收益 | 淘汰 |
| BF16+Slab8，正式 3072→1024 | 949.696 s，17.2518 tok/s；相对 BF16 baseline 约 -5.5% | 明确负收益 | 淘汰 |
| FP16 recurrent state | OOM 或 worker crash | 当前显存和实现不稳定 | 淘汰 |
| FP8 | 厂商执行栈出现不支持或断言错误 | 当前软件栈不可用 | 不支持 |
| 纯 FP16 Graph，第 1 次正式测试 | 858.574 s，19.0828 tok/s | 相对对应 BF16 baseline 约 +4.5% | **采用候选** |
| 纯 FP16 Graph，第 2 次正式测试 | 859.021 s，19.0729 tok/s | 与第一次差约 0.05%，结果可重复 | **采用** |

## 4. 当前最优方案

当前经过完整 3072→1024 验证的最优配置是：

```text
模型：Qwen3.6-27B
精度：FP16
拓扑：4 × TP2
单副本并发：C16
整机并发：C64
max-model-len：4096
KV blocks override：152
max-num-seqs：16
Graph 模式：FULL_DECODE_ONLY
Graph capture sizes：1, 2, 4, 8, 16
prefix caching：关闭
async scheduling：关闭
custom all-reduce：关闭
```

### 4.1 单副本正式结果

| 配置 | 第 1 次 | 第 2 次 | 平均吞吐 |
|---|---:|---:|---:|
| 纯 FP16 Graph | 19.0828 tok/s | 19.0729 tok/s | **19.0779 tok/s** |

以 GPU 0,1 的 BF16 baseline 18.2567 tok/s 为同副本对照：

- 第一次提升约 4.53%。
- 第二次提升约 4.47%。
- 两次平均提升约 4.50%。
- 两次 FP16 结果仅相差约 0.01 tok/s，重复性明显好于其他候选方案。

### 4.2 整机吞吐估算

在四个 TP2 副本能够保持单副本平均结果、且不存在新的跨卡资源争用时：

```text
19.0779 × 4 = 76.312 tok/s
```

相对 BF16 整机 baseline 72.781 tok/s，线性估算提升约 4.85%。该数值属于依据单副本正式结果得到的整机估算，不应写成已经完成的整机实测结果。

## 5. 性能瓶颈观测

纯 FP16 正式测试期间记录到的代表性数据如下：

| 指标 | 观测值 | 解释限制 |
|---|---:|---|
| 单芯平均核心利用率 | 约 91.8% | 表明正式运行中计算单元较繁忙 |
| 单芯显存占用 | 约 33.7 GiB | 当前 KV152/C16 可以稳定驻留 |
| 卡 0 平均功耗 | 约 301 W | 仅有部分逻辑设备提供可信功耗字段 |
| SMI 报告的显存利用率 | 固定约 58% | 空闲时也接近固定值，不能视为可信实时带宽利用率 |
| 根据 SMI 字段推导的带宽 | 约 584.6 GB/s | 因显存利用率字段疑似冻结，只能保留为原始记录，不能作为达成带宽结论 |
| Decode FLOPs 下界 | 约 1.03 TFLOPS/TP2 | 按 `2 × 27B FLOPs/token` 估算，未包含完整注意力开销 |
| 全流程 FLOPs 下界 | 约 4.12 TFLOPS/TP2 | 按总处理 token 数估算，未包含注意力二次项等额外计算 |
| Decode 理想权重算术强度 | 约 16 FLOP/Byte | 基于 batch=16、FP16 权重的简化理论估算，不是硬件计数器实测值 |

现有证据支持“执行期间核心利用率较高”，但还不足以严谨判断已经达到多少真实显存带宽利用率。当前 FANT SMI 的 memory utilization 字段存在冻结迹象，因此不能用其直接计算可信的 Roofline 带宽效率或实际 AI。

## 6. 与外部 916.48 数据的口径关系

外部表格中的 Qwen3.6-27B 数据为：BF16、`8×TP2`、并发 16、吞吐 916.48。该数值恰好接近：

```text
7.16 × 16 × 8 = 916.48
```

因此它更像是将单请求 Decode Avg TPS 乘以并发数和设备/副本计数得到的派生指标，而不是按照统一 wall-clock 计算的整机实际完成输出吞吐。

当前本项目的 72.781 tok/s baseline 和纯 FP16 约 76.312 tok/s 估算，采用的是实际完成 token 数除以端到端运行时间的口径。两者不能直接比较。正式对标时必须同时记录：

1. 整机 wall-clock output tok/s；
2. 每请求 Decode Avg TPS；
3. 并发数、请求数和副本数；
4. Prefill 是否计入计时；
5. TTFT 与请求尾部延迟；
6. 是否把单请求平均值再次乘以并发或芯片数量。

## 7. 结论与证据边界

1. KV blocks 144→152 是当前收益最大的配置修正，通过消除抢占将整机吞吐从 46.455 提升到 72.781 tok/s。
2. 在稳定的 KV152 BF16 baseline 上，纯 FP16 Graph 是目前唯一经过完整 3072→1024 测试并稳定获得正收益的计算优化，单 TP2 副本平均提升约 4.50%。
3. Slab、MTP 和权重转置在短 Decode 或单 GEMM 测试中曾出现明显提升，但均未通过完整长输入、长输出验证，说明微基准和短序列结果不能直接代表端到端吞吐。
4. 当前可以表述为“纯 FP16 在同一 TP2 副本的两次正式测试中稳定提升约 4.5%”。由于只有两次 FP16 重复、BF16 也不是多随机种子统计实验，不应表述为具有统计显著性。
5. 整机纯 FP16 的 76.312 tok/s 目前是线性估算值；在取得完整 C64 wall-clock 结果前，不应将其写成整机实测吞吐。
