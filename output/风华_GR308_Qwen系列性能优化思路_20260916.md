# 风华 GR308 Qwen 系列性能优化思路

版本：2026-09-16  
适用环境：GR308、vLLM 0.18.0、vllm_fant 1.1.0.20、BF16  
覆盖模型：Qwen3.6-35B-A3B、Qwen3.5-9B、Qwen3-30B-A3B、Qwen3-Next-80B-A3B-Instruct

## 1. 文档目标

本文档整理当前四个 Qwen 模型在 GR308 上的已验证配置、仍待确认的候选配置，以及下一阶段以高吞吐为主的优化路线。文档重点不是继续无边界地扩大参数矩阵，而是优先验证高概率方向，并用统一口径判断优化是否真实有效。

当前约束如下：

- 精度固定为 BF16。
- 自定义 all-reduce 必须保持启用，所有命令均不得加入 `--disable-custom-all-reduce`。
- 默认关闭 prefix caching，避免缓存命中干扰性能比较。
- 服务最大上下文长度为 4096，最大序列数为 16。
- 35B、9B、30B 使用 3072 输入、1024 输出；80B 使用 1024 输入、1024 输出。
- 短测中 C1 使用 16 prompts、C16 使用 32 prompts；正式测试中 C1/C16 均使用 64 prompts。
- 每次只改变一个主要变量；跨卡重复、完整输出和硬件清理结果必须一并记录。

## 2. 当前结果与配置基线

| 模型 | 当前配置 | C1 TTFT | C1 Decode TPS | C16 TTFT | C16 Decode TPS | C16 聚合吞吐 | 结果性质 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | --- |
| Qwen3.6-35B-A3B | TP2 / MTP4 / Graph 4–64 / batch 4096 / 自动 KV / block 1088 / 同步 | 1537.19 ms | 50.75 | 3321.47 ms | 13.93 | 180.64 tok/s | 短测候选 |
| Qwen3.5-9B | TP1 + DP2 / MTP4 / Graph 4–32 / batch 4096 / 自动 KV / block 800 / 同步 | 2335.93 ms | 54.64 | 3501.62 ms | 18.90 | 247.16 tok/s | 正式结果 |
| Qwen3-30B-A3B | TP2 / 无 MTP / 无 EP / Graph 4–32 / batch 4096 / 固定 8 GiB KV / block 800 / async | 1054.43 ms | 26.43 | 4225.69 ms | 15.22 | 225.67 tok/s | 正式结果 |
| Qwen3-Next-80B-A3B-Instruct | TP4 / MTP1 / Graph 4–64 / batch 2048 / 固定 8 GiB KV / block 1088 / 同步 | 595.37 ms | 28.86 | 3528.79 ms | 16.20 | 231.98 tok/s | 短测候选 |

结果解释：

- 9B 是当前绝对吞吐最高的配置，主要收益来自双 TP1 / DP2、MTP4 和自动 KV。
- 30B 在不开 EP 的情况下获得更稳定的 C16 吞吐；现有软件栈下，EP 尚未证明能够稳定带来收益。
- 35B 的 MTP4 / batch4096 组合首次同时超过对照表的 C16 Decode TPS 和 TTFT，但仍需正式复测。
- 80B 的主要收益来自 MTP1；Graph64 对 C16 Decode TPS 有进一步增益，自动 KV 则在本轮启动失败。

## 3. 统一优化方法

### 3.1 优化目标排序

本轮以高吞吐为第一目标，指标优先级为：

1. C16 Decode Avg TPS。
2. C16 聚合输出吞吐。
3. 请求完整率和运行稳定性。
4. Median TTFT。
5. C1 Decode Avg TPS。

如果多个配置的 C16 Decode TPS 差距不超过 3%，优先选择 TTFT 更低、跨卡方差更小、启动与清理更稳定的配置，而不是机械选择单次最高值。

### 3.2 测试分层

每个新方向按三层推进：

1. **微型准入**：启动、warm-up、短输出正确性、Graph 捕获、MTP 接受率和显存检查。
2. **短测筛选**：C1 16 prompts、C16 32 prompts，用于快速排除负收益方向。
3. **正式确认**：C1/C16 各 64 prompts，至少跨两张物理卡重复；最终候选建议再执行 3 个固定 seed。

只有正式确认结果才能作为部署结论。短测只用于排序候选，不能替代验收。

### 3.3 每轮必须记录的证据

- 完整 `vllm serve` 启动参数和镜像 digest。
- 模型目录、权重身份、MTP 配置及实际接受率。
- Graph capture sizes、Graph 捕获和回放计数。
- C1/C16 的 TTFT、TPOT、ITL、Decode Avg TPS、聚合吞吐。
- completed、failed 和每条请求的实际输出长度。
- 启动前后显存、温度、核心健康以及容器清理状态。
- 物理卡编号、逻辑设备编号、CPU 亲和性和运行 seed。

## 4. Qwen3.6-35B-A3B 优化路线

### 4.1 首要任务：确认 D 组是否可复现

当前最优 D 组为 MTP4、Graph `[4,8,16,32,64]`、batch4096、自动 KV、block1088。它比此前正式配置的 C16 Decode TPS 和聚合吞吐更高，但样本量较小，因此第一优先级不是继续增加新参数，而是完成以下确认：

- 在至少两张不同物理卡上各重复一次短测。
- 完成 C1/C16 各 64 prompts 的正式测试。
- 对比 MTP 接受率、平均接受长度和 Graph 命中率，确认收益来自 MTP4，而不是单次运行波动。
- 检查 C16 TTFT 和吞吐是否能同时保持，不接受以大量失败或输出不足换取的表面 TPS。

### 4.2 后续高概率方向

1. **MTP 深度和接受率联合优化**  
   在同一 Graph、batch 和 KV 配置下，对 MTP3、MTP4 做正式 A/B。MTP4 已显示较高 Decode TPS，但还应结合 draft acceptance 和每步验证成本判断。若 MTP4 接受率波动大，可测试 MTP3 与 MTP4 的业务分档，而不是只保留单一配置。

2. **Graph 桶精简**  
   对比 `[4,8,16,32,64]`、`[1,2,4,8,16,32,64]` 和 `[4,8,16,32,64,128]`。目标是确认小 batch 桶是否改善 C1，以及 128 桶是否对 C16 有收益。若无收益，应使用更小的捕获集合以减少启动时间和显存开销。

3. **Batched tokens 局部搜索**  
   以 4096 为中心测试 3072、4096、6144。此前 2048、3072、4096 的结果表明该参数对 TTFT 和吞吐均有影响，但不是单调关系。任何更大值必须先通过显存和完整输出准入。

4. **自动 KV 与固定 KV 对照**  
   35B 的自动 KV 已成功运行，建议正式比较自动 KV 与固定 8 GiB，记录实际可用 block 数、峰值显存和 C16 驻留能力。自动 KV 若稳定，应优先于人为限制 8 GiB。

5. **跨卡拓扑和 CPU 亲和性**  
   当前结果存在明显的卡间和启动时序影响。应固定 CPU NUMA、错峰初始化 FHCCL/RCCL communicator，并在同一配置下做跨卡重复，避免把拓扑差异误判为参数收益。

### 4.3 不建议继续投入的方向

- block800 已出现启动失败，35B 暂时固定 block1088。
- async scheduling 没有显示出稳定优势，高吞吐候选继续使用同步调度。
- `fuse_gemm_comms`、`fuse_allreduce_rms` 相关候选曾启动失败，不应在缺少后端兼容证据时直接加入正式配置。
- 不以禁用 custom all-reduce 作为规避故障手段。

## 5. Qwen3.5-9B 优化路线

### 5.1 当前判断

双 TP1 / DP2、MTP4、Graph `[4,8,16,32]`、batch4096、自动 KV 是当前高吞吐最优方案。其 C16 Decode TPS 和聚合吞吐均为四个模型最高，但 TTFT 高于 TP2 对照，因此应把吞吐档和低延迟档分开维护。

### 5.2 后续方向

1. **DP2 负载均衡验证**  
   分别统计两个 TP1 replica 的请求数、队列时间、输出吞吐和尾延迟，确认 247.16 tok/s 不是短时间调度偏差。必要时显式使用两个端口和外部轮询，与 vLLM 内部 DP2 做对照。

2. **单 replica 并发配比**  
   在总并发 16 下测试每个 replica 的 8+8、6+10 等分配，观察是否存在单实例最优并发点。若 8+8 最稳，应将其固化为服务层并发上限。

3. **MTP3/MTP4 正式对照**  
   MTP4 当前吞吐最好，但应补充接受率、拒绝率及 draft 开销。若低并发业务更看重 TTFT，可保留 MTP3 或 TP2 作为低延迟档。

4. **Graph32/64 对照**  
   当前 Graph32 已表现良好。Graph64 只需进行一次隔离短测；若 C16 收益不足 3%，不扩大正式矩阵。

5. **自动 KV 稳定性**  
   连续冷启动三次，记录自动分配的 KV block 数及显存余量。Qwen3.5 属于混合状态模型，不能只依据通用 Transformer 的 KV 估算判断容量。

## 6. Qwen3-30B-A3B 优化路线

### 6.1 当前判断

该模型没有原生 MTP 权重。当前最佳方案是 TP2、不开 EP、Graph `[4,8,16,32]`、batch4096、固定 8 GiB KV、block800、async scheduling。其 C16 Decode TPS 比对照明显提升，但 TTFT 增加，属于吞吐优先配置。

### 6.2 后续方向

1. **Async 调度边界**  
   对 C4、C8、C16 分别比较同步和异步调度，确定 async 从哪个并发开始产生净收益。若只在 C16 有收益，应按业务并发动态选择服务档位。

2. **MoE backend 对照**  
   在其他参数不变时比较默认 auto 与 Triton backend，重点记录 expert routing、kernel 时间和启动稳定性。若 Triton 收益不足 3% 或出现回归，保持 auto。

3. **Batch 4096 周边搜索**  
   测试 3072、4096、6144，观察 C16 Decode TPS 与 TTFT 的拐点。固定 8 GiB KV，避免同时改变 KV 容量造成混淆。

4. **Graph64 单变量验证**  
   当前 Graph32 为稳定基线。只追加一次 Graph64 短测；若没有稳定吞吐增益，不进入正式复测。

5. **EP 作为独立兼容性课题**  
   EP 在当前软件栈下未稳定运行，不纳入近期高吞吐主线。只有在 FHCCL/RCCL 初始化、专家 all-to-all 和内存布局问题得到独立解决后，才重新比较 EP+TP2 与纯 TP2。

## 7. Qwen3-Next-80B-A3B-Instruct 优化路线

### 7.1 首要任务：正式确认 Graph64 候选

当前高吞吐候选为 TP4、MTP1、Graph `[4,8,16,32,64]`、batch2048、固定 8 GiB KV、block1088。短测中 C16 Decode TPS 为 16.20，TTFT 为 3528.79 ms。应优先补齐跨两组物理卡和 64+64 prompts 的正式测试。

### 7.2 后续方向

1. **MTP1 接受率诊断**  
   MTP1 是 80B 的主要增益来源。正式测试需要记录每轮 draft、accepted tokens 和拒绝比例，确认长时间运行后接受率不会衰减。

2. **Graph32/64/128**  
   Graph32 与 Graph64 的差距较小，但 C16 以 Graph64 更好。可追加 Graph128 单变量短测；若收益不足 3% 或启动显存明显增加，则保留 Graph64。

3. **吞吐档与 TTFT 档分离**  
   batch2048 的 C16 Decode TPS 为 16.20；batch4096 的 C16 Decode TPS 为 16.02，但 TTFT 从约 3529 ms 降至约 2975 ms。建议保留两套配置：batch2048 用于高吞吐，batch4096 用于较低首包延迟。

4. **固定 KV 容量搜索**  
   自动 KV 已在初始化阶段失败，不应直接用于正式部署。可在固定模式下测试 8、10、12 GiB，逐级验证启动、C16 完整率和显存余量；每次只调整 KV 容量。

5. **TP4 拓扑绑定**  
   80B 跨两张物理卡，应固定相邻逻辑设备、CPU NUMA 和 communicator 启动顺序。需要把拓扑变化作为独立变量，而不是与 MTP、Graph 同时调整。

## 9. 四卡资源编排建议

四张物理卡共八个逻辑设备。35B、9B、30B 各占一张物理卡，80B 占两张物理卡，因此四个模型无法在当前最优拓扑下同时运行。

建议分两波执行：

### 第一波：三模型并行筛选

- 物理卡 0（逻辑 0、1）：35B。
- 物理卡 1（逻辑 2、3）：9B。
- 物理卡 2（逻辑 4、5）：30B。
- 物理卡 3（逻辑 6、7）：保留给 35B 跨卡重复或故障隔离。

服务启动必须错峰。只有前一个模型的 API 和 EngineCore 真正 ready 后，才启动下一个模型，避免多个 FHCCL/RCCL communicator 同时初始化。

### 第二波：80B 独占两卡

- 物理卡 2、3（逻辑 4–7）：80B TP4。
- 物理卡 0、1：用于 35B/9B 的重复测试，或保持空闲作为健康对照。

80B 与占用逻辑 4、5 的 30B 不得同时启动。

## 10. 正式验收标准

一个配置只有同时满足以下条件，才可标记为正式可用：

- C1/C16 各 64 个请求全部完成，failed 为 0。
- 每个请求实际生成 1024 tokens，不能把截断响应计入吞吐。
- 跨至少两张物理卡重复后，C16 Decode TPS 变异不超过 5%。
- 高吞吐候选相对当前正式配置的收益至少为 3%，或在吞吐持平时带来明确 TTFT 改善。
- Graph 确实捕获并回放；MTP 配置有实际 draft/accepted 证据。
- 无设备核心错误、通信 reset、后端 fatal error 或残留容器。
- 测试后逻辑设备显存回落到约 500–540 MiB 的空闲范围。
- 启动参数中不包含 `--disable-custom-all-reduce`。

## 11. 阶段性结论

近期最值得投入的工作是完成 35B D 组和 80B Graph64 组的正式复测，而不是继续无边界扩大参数矩阵。9B 已具备较明确的高吞吐部署方案，下一步重点是 DP2 的负载均衡和稳定性；30B 则应围绕无 EP 的 TP2 路线继续优化 async、batch 和 MoE backend。EP、自动 KV（80B）以及尚未证明兼容的编译融合选项应从主线中隔离，先作为独立稳定性课题处理。
